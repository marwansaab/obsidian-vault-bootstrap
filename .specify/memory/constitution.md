# obsidian-vault-bootstrap Constitution

## Core Principles

### I. Deterministic & Reproducible Rendering (NON-NEGOTIABLE)

Same profile + same source-repo version + same templates MUST produce byte-identical output across machines and across re-runs. Rendered files MUST NOT contain timestamps, UUIDs, machine names, working-directory paths, environment-variable values, or any other non-deterministic content. Where a timestamp is genuinely required (e.g. an `Initialise-Vault.md` runbook noting when the vault was first bootstrapped), it MUST be derived from a profile field, never `new Date()`. Random ordering of map/object keys MUST be normalised before render.

**Rationale**: Consumer projects commit the rendered `CLAUDE.md` + `.claude/` + vault folder to their own Git repos. If the renderer is non-deterministic, every re-run produces spurious diffs, masking intent-driven changes under rendering noise and making it impossible to review upgrades cleanly.

### II. Single Source of Truth

Instruction content and vault templates live only in the source repo under `core/` + `families/<family>/` + `templates/`. Per-project rendered output MUST NOT be edited by consumers; the renderer MUST stamp a verbatim header — `<!-- DO NOT EDIT — regenerated by @marwansaab/obsidian-vault-bootstrap@<version>. Re-run the bootstrap to update. -->` (or the language-appropriate comment equivalent for non-markdown outputs) — on every output file. The renderer SHOULD additionally emit a sample pre-commit hook the consumer project can install to verify render parity at commit time.

**Rationale**: The channel's value is single-source-of-truth — a rule clarification at the master propagates via opt-in version-bumps to every consumer. Consumer-side edits to rendered output break that property silently; the header turns silent breakage into visible warning.

### III. LLM-Agnostic Agent-Instruction Generation

The renderer MUST support producing agent-instruction files for multiple AI coding assistants from the same source content. LLM-specific output (filenames, frontmatter shapes, syntax conventions — e.g. `CLAUDE.md` for Claude Code, `.cursor/rules/*.mdc` for Cursor, `.clinerules` for Cline, `.windsurf/rules/*.md` for Windsurf) MUST be expressed in template families parameterised by the profile's `agents:` array, NEVER hardcoded in renderer logic. Adding support for a new assistant arrives as a new template family + a profile-enum entry, NOT as a renderer code branch.

**Rationale**: The package's value proposition is LLM-agnosticism. Hardcoded `CLAUDE.md` references in the renderer would break every non-Claude consumer the moment the rendering logic touches output-shape concerns.

### IV. Boundary Input Validation with Zod

Every input that crosses a process boundary — profile YAML, CLI arguments, environment variables, interactive Q&A responses, and any externally-fetched content — MUST be validated through a `zod` schema before any business logic, filesystem write, or template render runs. The schema is the single source of truth for both the published shape (documented for users) and the runtime parse. Validation failures MUST return a structured error reporting the field paths zod produces and a human-readable explanation. The zod-inferred type (`z.infer<typeof schema>`) MUST be the canonical type used downstream; redefining the same shape as a TypeScript interface elsewhere is a violation. Internal helpers MAY trust their inputs.

**Rationale**: A profile typo or missing field caught at render time produces opaque template-engine errors. The same typo caught at the boundary produces an actionable message naming the offending field.

### V. Explicit Failure Propagation

Filesystem errors, template-engine errors, npm errors, Git errors, and Q&A-flow interruptions MUST be surfaced to the user as structured errors with clear remediation hints. `catch` blocks MUST NOT return empty results, default values, or `null` to mask a failure. If a partial-success path is intentional (e.g. continuing after a non-critical template warning), it MUST cite the explicit decision (a Clarifications entry or an ADR) and the renderer's output MUST report what succeeded AND what was skipped. Errors propagated to callers MUST be instances of a project-defined `class RenderError extends Error` (or a discriminated subclass) carrying at minimum: `code` (stable string), `cause` (original error), and `details` (structured record with field paths / file paths / template names). Plain `throw new Error("...")` at any boundary surface is a violation.

**Rationale**: A partial-success bootstrap leaves the consumer in a worse state than a clean error — they don't know what failed. Typed errors let reviewers grep for `RenderError` to audit every place a failure crosses a boundary.

### VI. Caveman Compression for Agent-Facing Templates

Templates that produce files destined for agent / LLM consumption — the operative rule content of `CLAUDE.md`, `.cursor/rules/*.mdc`, `.clinerules`, `.windsurf/rules/*.md`, `.continue/rules/*.md`, agent system prompts, and any source-repo `core/` + `families/*` instruction content — MUST be authored in caveman full compression (drop articles, filler, pleasantries, hedging; fragments OK; short synonyms; technical terms exact; code blocks unchanged; error strings verbatim; function / API / parameter / file names never abbreviated). Templates that produce files destined for human consumption — `README.md`, `CHANGELOG.md`, profile schema documentation, design docs — stay in normal prose. Mixing the two audiences in a single template file is a violation.

**Rationale**: Token economy on the consumer side requires that the rendered agent-facing files be compressed (target ~75% size reduction vs prose). Authoring the compression directly into the source templates produces compressed output natively rather than relying on a post-render compression pass that could drift.

### VII. Attribution & Layered Composition Transparency

Any module whose algorithm, structure, or non-trivial code derives from another project MUST carry a header naming the upstream source, license SPDX identifier, pinned commit hash or version, and a one-line description of what was lifted vs adapted. Original modules — those with no upstream — MUST carry a header of the form `// Original — no upstream. <one-line intent>.` Modules without any header (neither attribution nor original-contribution) are a violation regardless of actual provenance — the absence of a header is indistinguishable from forgotten attribution. README MUST list every upstream in an `## Attributions` section with the same SPDX + version metadata.

**Rationale**: Transparency about what was built vs composed is a quality signal and a legal hygiene requirement. It also lets future maintainers upgrade lifted code by tracing each layer back to its source.

## Technical Standards & Stack Constraints

- **Language**: TypeScript, strict mode, `tsc --noEmit` clean. No `any` in public signatures; `unknown` only when immediately narrowed via zod.
- **TypeScript config**: `tsconfig.json` MUST set `"module": "NodeNext"`, `"moduleResolution": "NodeNext"`, `"target": "ES2024"` (or higher matching the `engines.node` floor), `"strict": true`.
- **Runtime**: Node.js >= 22.11 (latest 22.x LTS at ratification). Set `engines.node` in `package.json` accordingly.
- **Templating**: Substitution-only interpolation of `{{name}}`-style tokens via the project-local `interpolate()` function in `src/render/interpolate.ts`. Full template engines (Handlebars, Nunjucks, Liquid, etc.) are forbidden without a future amendment per ADR-020 (Template Substitution Engine Choice, Decided 2026-05-18).
- **Validation**: `zod` is the only permitted runtime input-validation library at any boundary surface. Hand-rolled `typeof` / `instanceof` chains at boundaries are a violation.
- **YAML parsing**: `js-yaml`. Other parsers require justification.
- **Glob matching**: `glob` or `fast-glob`.
- **Interactive Q&A**: `@inquirer/prompts` (or equivalent maintained interactive-prompt library). CLI argument parsing: built-in `node:util` `parseArgs`.
- **Test framework**: `vitest` with `@vitest/coverage-v8` for the V8 coverage provider. Test files use the `*.test.ts` naming convention, co-located with their source module.
- **Lint & format**: `eslint` (flat config) MUST pass with zero warnings before merge. Prettier is the formatter of record.
- **Dependencies**: New runtime dependencies MUST be justified in the PR description against the alternative of a small in-tree implementation. Bias hard toward in-tree for anything under ~150 LOC or with a narrow surface area.

## Development Workflow & Quality Gates

1. `npm run lint` passes with zero warnings.
2. `npm run typecheck` passes.
3. `npm run build` succeeds.
4. The test suite covering all public surfaces passes — every CLI command, every renderer entrypoint, and every Q&A flow ships with happy-path AND failure-or-boundary tests in the same change that adds or modifies it.
5. Aggregate **statements** coverage threshold passes — configured in `vitest.config.ts` under `test.coverage.thresholds.statements`. This is the single source of truth for the merge floor; it ratchets via a one-line visible edit. Branch / function / per-file thresholds are forbidden without an amendment.
6. The Sync Impact Report at the top of the constitution file is updated whenever the constitution itself is amended.
7. Spec-driven changes (those produced via `/speckit-plan` and `/speckit-tasks`) MUST pass the Constitution Check gate documented in the plan template before implementation begins.
8. Every PR description includes a Constitution Compliance checklist with one Y / N / N/A entry per principle:

   - [ ] Principle I (Deterministic & Reproducible Rendering): Y / N / N/A
   - [ ] Principle II (Single Source of Truth): Y / N / N/A
   - [ ] Principle III (LLM-Agnostic Agent-Instruction Generation): Y / N / N/A
   - [ ] Principle IV (Boundary Input Validation with Zod): Y / N / N/A
   - [ ] Principle V (Explicit Failure Propagation): Y / N / N/A
   - [ ] Principle VI (Caveman Compression for Agent-Facing Templates): Y / N / N/A
   - [ ] Principle VII (Attribution & Layered Composition): Y / N / N/A

   Any `N` MUST be paired with a Complexity Tracking entry in the corresponding plan justifying the deviation. `N/A` is permitted only when the change touches no surface the principle governs (e.g., a docs-only PR is N/A on I and VI; a PR that adds no boundary entry point is N/A on IV; a PR that adds no new agent template family is N/A on III).

**Spec-kit workflow**: Any feature larger than a single-file change MUST enter via `/speckit-specify` → `/speckit-clarify` (repeated until no underspecified items remain) → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`. Spec Clarifications log every Q&A so later readers can trace each decision back to the conversation that produced it. The plan's Constitution Check table cites how each principle is satisfied OR documents and justifies any deviation. `tasks.md` is dependency-ordered.

Code review MUST verify each gate explicitly; "CI is green" is necessary but not sufficient — reviewers also confirm Principles I–VII by inspection.

## Governance

This constitution supersedes all other contributor guidance, including `README.md`, agent prompts, and prior conventions. Where this document and another guide disagree, this document wins; the other guide MUST be updated to match within the same change set.

**Amendment procedure**: Amendments are proposed by editing this file via `/speckit-constitution`, which regenerates the Sync Impact Report, bumps the version per the rules below, and updates the `Last Amended` date. Amendments MUST be reviewed in a dedicated PR — never bundled with feature work.

**Versioning policy** (semantic versioning of the constitution):

- **MAJOR**: A principle is removed, redefined in a backward-incompatible way, or a governance rule is reversed.
- **MINOR**: A new principle or normative section is added, or existing guidance is materially expanded or contracted in scope.
- **PATCH**: Wording clarifications, typo fixes, rationale rewrites that do not change the rule.

**Runtime guidance**: Day-to-day development guidance lives in `CLAUDE.md` and in feature-specific plans under `specs/`. Those documents MUST defer to this constitution; if they imply a contradiction, treat it as a bug in the guidance document and fix it.
